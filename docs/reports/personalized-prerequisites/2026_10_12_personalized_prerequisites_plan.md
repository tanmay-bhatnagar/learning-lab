# Personalized prerequisites — research and design discussion

Date: 12 October 2026. Status: planning only; application implementation is not authorized by this task. Coordinator owns this consolidated decision note and Git; research/design are read-only and run sequentially to completion.

## Settled user requirements

- The feature is on demand and uses the same selected local Ollama model.
- A CV supplied for this purpose is mandatory. If unavailable, ask for it and block this feature; do not replace the requirement with a questionnaire-only path.
- Use the CV to tailor high/medium-level learning requirements. A requirement such as basic Python must not expand into a library-by-library syllabus.
- The CV describes experience, not demonstrated mastery. EACH requirement asks whether the user is already comfortable with it; there is no single familiarity question for the entire list.
- User feedback guides refinement. Deeper discussion or a course can develop in the existing main conversation; no side conversation or autonomous course-generation workflow is implied.
- Preserve separate cohesive modules, explicit dependencies, runtime policy/context boundaries, topic isolation, originals and clear generated-content provenance.

## Design checkpoint — completed without interruption

Design (Sol Medium) finished after research and used its evidence; no new experiments or application edits. The [separate design report](2026_10_12_personalized_prerequisites_design.md) proposes contracts, module ownership, milestones and validation gates. Neither role was interrupted.

Recommended feedback flow: all requirement cards together, EACH independently questioned and editable. Answers are self-reports: comfortable lowers preparation priority, refresher suggests short review, new suggests foundations, uncertain asks clarification, unanswered remains pending. Saving them causes no inference. Explicit versioned handoff to the selected existing main conversation supplies refinement context; an editable draft is not automatically sent. This is simpler/cheaper than per-answer model calls and keeps deeper course discussion in ordinary chat. No global skill/mastery profile or forced all-answered gate is recommended.

The app must supply EVERY familiarity question deterministically, bind requirements to original section evidence and CV refs, buffer structured generation until provider completion/validation/save, and keep learner-dependent assessment/answer versions separate from native map state. Complete inputs and fresh runtime policy use the existing shared local gateway; optional schema support is recommended over a separate client/framework. Local compatibility and pedagogical quality remain open, with an isolated synthetic spike as the first technical validation step. No ready-feature claim is justified yet.

Two pending user choices: topic CV versus reusable workstation CV with explicit topic access, and searchable PDF only versus also accepting pasted actual CV text. Topic scope/PDF-only are role recommendations for the smallest first version, not silent settled choices. Proposed defaults also need discussion: visible optional topic goal with reading default, pending answers allowed, main-chat refinement and revoke-future-use rather than erasure. Revocation preserves originals and historical imported context; it must not be labeled delete/forget. Global reuse or physical erasure changes require explicit revised contracts.

Planning work uses no personal CV. Application implementation remains unstarted pending discussion/authorization. Two role reports are separate; this plan is the consolidated synthesis. Earlier dated plans and implementation notes remain preserved.

## Ongoing learning context — user clarification, 12 October 2026

Tanmay requires saved familiarity answers and the learning/preparation plan to inform answers throughout the actual learning chat. This supersedes reliance on the earlier one-time imported snapshot alone; preserve that design report as history. Existing chat includes its topic goal separately but treats imported context as ordinary history, which can be trimmed (`services/api/lab/chat_prompt.py`, `chat_session.py`, `context.py`). A transcript snapshot cannot guarantee current preparation state on later requests.

Recommended persistence: versioned structured topic-local JSON for server-owned proposals, exact requirement IDs, editable user self-reports/clarifications and an active learning/preparation plan. Human-readable Markdown can be rendered/exported from that authoritative state; PDF can be an optional export, not the state that must be reparsed. Existing chat history remains separately saved JSON. No such prerequisite/plan records are implemented yet, and exact filenames/schema remain a design decision.

Recommended prompt boundary: resolve the selected active plan and latest saved answers afresh for EACH applicable learning-chat request, construct a compact deterministic learner-context block, and count it in preflight alongside runtime policy, topic goal, evidence, history and question. Loading/formatting saved state uses no additional model call. Distinguish CV evidence, model-inferred recommendations, user self-reports and any future verified observations; learner context is not a tool/access permission or proof of mastery. Do not silently discard required current context on budget overflow. Imported messages remain useful historical snapshots, while the current saved state supplies freshness.

Open design questions: topic-wide versus conversation-selected active plan; how revoked/replaced CVs and changed source/goal affect ongoing context; keeping historical imports distinct from newer active answers; how user statements in free-form chat become explicit saved updates. Recommend user-confirmed plan/comfort changes rather than inferring mastery or silently rewriting records from a casual chat comment. Broader progress/assessment memory is not automatically included in this change. Implementation must test latest answers on the next request, long-history trimming, reload, conversation/topic isolation, budget failures and visible stale/revoked context behavior. Coordinator owns the revised contract; implementation is still not started.

## Compact context and manual proficiency — user clarification, 12 October 2026

The user requires context-friendly, inexpensive attachment of current learner state. Separate authoritative versioned JSON from its compact model-facing projection. Keep record IDs, history, provenance and validation metadata in storage; send concise relevant concept/comfort pairs, current goal/focus and necessary qualifications, rather than full JSON, CV or historical plan on every chat turn. Projection is deterministic and requires no extra inference. Measure prompt cost and make budget/relevance behavior explicit before promising token savings; do not silently omit important current answers.

The proposed Save familiarity change action is a mechanism for updating authoritative proficiency JSON, not a new conversation or separate model workflow. Existing prerequisite controls and explicit user-confirmed changes from main chat should use the same validated/versioned state-update boundary. Casual chat or a model inference must not silently become a proficiency claim. Exact UI placement and how proposed chat changes are surfaced remain design details.

Add a **My proficiency** section for user-authored concepts/skills (these are not new Learning Lab workspace topics). The user can add an entry, set Comfortable / Needs a refresher / New to me / Not sure, optionally clarify what that means, and edit existing entries including corrections to model-suggested preparation. Manual entries and answers are labeled user self-report and kept distinct from model recommendations/CV evidence; entry provenance must remain clear. Changes persist in the same proficiency state and affect the next applicable chat's compact context with no model call.

Manual entries must not disappear on assessment regeneration. They are an additive requirement superseding the earlier assessment-only response recommendation; original research/design reports remain preserved. EACH model-proposed requirement still presents its familiarity question even when an existing user entry or CV mentions the concept. Do not copy answers across similar names or treat a broad comfort entry as mastery of a specialized subtopic. Manual editing does not substitute for the CV required to generate personalized prerequisites.

Implementation follow-up: settle profile/answer scope and explicit entry association, current versus historical values, duplicate labels, conflict-safe edits and context relevance/budget rules. Validate manual add/edit/reload, preservation across regenerated proposals, no-inference saves, correction precedence, individual requirement questioning, and latest compact context on subsequent main-chat requests. This is a planning update; no proficiency JSON or UI has been implemented.

## Naming, shared CV and optional full-CV context — user decisions, 12 October 2026

Use **My proficiency** as the single product name for the proficiency list and its add/edit/save mechanisms. Earlier Update my plan / Save familiarity change names are superseded; no separate feature or conversation is intended. The learning plan remains distinct: intended study versus self-reported current familiarity.

The user chooses CV reuse across topics. Topic-only CV storage is therefore superseded as the intended product scope. Design must provide explicit controlled access to the registered shared learner CV, not broad reads of other topics or arbitrary file paths. The user requests ingestion like ordinary documents: reuse the normal document parsing/text/provenance pipeline and applicable indexing, with CV identity/purpose and cross-topic access handled explicitly. Earlier dedicated acquisition/no-index recommendations remain history and must not be silently carried into the revised implementation as settled requirements.

Normal learning chat uses compact current My proficiency/goal/focus context; full CV is omitted by default once background-based preparation has been considered. CV can be read again for explicit prerequisite generation when needed. Add an **Always include CV** option for the user's context experiment: when enabled, EACH applicable chat request includes the current CV's complete extracted document text in the same untrusted document-evidence representation used by the app, not the original PDF binary and not only a query-selected subset. A per-conversation toggle consistent with existing attachment preferences is recommended, so experiments can keep separate CV-on/CV-off chats; exact scope/UI persistence is a remaining contract detail.

Verified repository behavior: indexed Docling attachments use query-dependent top-k retrieval (`services/api/lab/web/chat.py:166–198`); unindexed attachments supply converted Markdown. The existing budget planner can remove/shorten attachment/history context (`context.py`). Thus ordinary file selection alone does not guarantee complete CV on every turn. The optional full-CV mode needs explicit retained-input budgeting and must refuse visibly before inference if required current policy/question/proficiency/CV cannot fit; no silent CV trimming, omission, generated replacement or background summarization. Keep full CV cost visible in context accounting. Extracted text is appropriate, but cheapest context depends on selected text amount and tokenizer, not merely Markdown versus JSON; no claim that full-CV mode is cheapest.

CV-disabled mode must exclude CV from ordinary study retrieval/context unless separately explicitly requested; shared CV registration cannot make every study request retrieve it accidentally. Preserve source identity/revisions, clear CV-versus-study evidence and user self-report distinctions. Future implementation must validate toggle-off exclusion, toggle-on complete/latest CV every turn despite query relevance or long-history pressure, context-fit failures, conversation setting persistence/isolation, and authorized shared-CV access.
